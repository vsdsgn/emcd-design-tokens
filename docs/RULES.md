# Правила поведения агента

Как работаем в этом репозитории. Правила дизайн-системы — в `docs/agent-brief-ds2.md`, `docs/component-contract.md`, `docs/patterns.md`. Ошибки, из которых выросли правила, — `docs/LESSONS.md`.

## 1. Начало сессии

1. Читать по порядку: `docs/HANDOFF.md` → `docs/OPEN-QUESTIONS.md` → `docs/HOW-IT-WORKS.md` → `docs/LESSONS.md` → этот файл.
2. Вывести Стефану два-три пункта: текущий этап, что делаем сейчас, какие уроки касаются задачи (номера `L-NNN`).
3. Проверить, нет ли параллельного писателя: другие сессии Claude, свежие незакоммиченные файлы. Если есть — решить, кто владеет файлом, до правок.
4. Работа ведётся на VPS `/srv/emcd-design-tokens` от пользователя `stephane`; репозиторий публичный, секретов в нём нет.

## 2. Во время работы

- **Автономно до результата.** Рутину (экспорт Foundations, `npm run all`, таблица миграции, push) делаем сами, без вопросов.
- **Новая идея:** быстрая и безопасная — делаем; иначе в парковку `OPEN-QUESTIONS` (L-018).
- **Перед новым дизайном** ищем в legacy DS Web / App и продуктовых файлах. Не рисуем с нуля, не копируем 1:1 без пересадки на правила 2.0 (L-016, L-017).
- **Пилот до пакета:** 1–2 эталона, проверки, потом пакет (L-001).
- **Порядок сборки:** эталон → библиотеки → компонент → Publish → экран → аудит (`docs/BUILD-RULES.md`, §1). Список замечаний Стефана — чеклист, в отчёте каждый пункт (L-022).
- **После каждой привязки или замены** в Figma — скриншот и чтение отдельным вызовом (L-007, L-011).
- **Скрипты Figma:** читать `LESSONS.md` раздела B перед написанием; страницы — по имени, не по индексу (L-013); не вызывать `resetOverrides` (L-006).
- Ответы Стефану: коротко, по пунктам, по-русски.

## 3. «Готово»

Пишем «готово», только когда выполнено всё:

1. Проверены все варианты, оси и свойства компонента (не выборочно).
2. `audit.plugin.js`, `variables-check.plugin.js`, `audit-parity.plugin.js` чистые; для сборки кода — `npm run all`, `npm run a11y`, `npm run exceptions`, `npm run parity`.
3. Ручной чеклист (`docs/preflight.md`, «Что скрипт не ловит») пройден; для beta — стенд просмотрен глазами (`docs/HOW-IT-WORKS.md`, «Перевод набора в beta»).
4. Замечание закрыто правилом в скрипте, а не одной правкой (L-002).
5. Запись в `HANDOFF.md` (коротко) и, если была ошибка, в `LESSONS.md`.

В отчёте — что проверено и что не проверено. Непроверенное не называем готовым.

## 4. Только с «ок» Стефана

- Изменение существующих токенов Foundations, публикация, статусы `stable`, удаление компонентов. Новые токены завести можно, публикует Стефан. После Publish Foundations — Update all в Components (его действие).
- Пакет правок в Figma без снимка Version history (L-005).
- Любое действие во внешних системах: сообщения, публичные посты, прод-репозитории разработки (`ds-playground` и т. п. не клонируем).
- Архивные страницы (`🗄`, ниже `---`) не трогаем.

## 5. Ошибки

1. Совершили ошибку или услышали «опять» — **сразу** запись в `docs/LESSONS.md`: симптом, причина, правило, проверка.
2. Если ошибку можно поймать скриптом — правило в скрипт (`audit-parity.plugin.js`, `scripts/exceptions-check.mjs`, `scripts/parity.mjs`, `tests/`), и только потом исправление.
3. В шапке скрипта или рядом с кодом, где ошибка возможна, комментарий: `// См. docs/LESSONS.md#l-NNN`.
4. Повторилась ошибка из реестра — это дефект проверки: усилить правило, а не только поправить результат.

## 6. Конец сессии

1. Закоммитить и запушить (по правилам репозитория), если есть изменения.
2. `HANDOFF.md`: что сделано, что остановлено и почему, следующий шаг. Не более нескольких строк на тему; подробности — в профильные доки.
3. `LESSONS.md`: новые записи из этой сессии.
4. Открытые вопросы к Стефану — в `OPEN-QUESTIONS.md`.
