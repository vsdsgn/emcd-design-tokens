# Задание: просмотр стенда и запись контракта для наборов EMCD DS 2.0

Ты проверяешь компоненты дизайн-системы EMCD DS 2.0 перед переводом из draft в beta. В Figma ничего не меняешь и к Figma не обращаешься: работаешь только с файлами. В репозитории `/srv/emcd-design-tokens` ничего не правишь, git не трогаешь.

База: `S` — рабочая папка стенда (листы `sheets/`, описания `descs/`, выжимки манифеста `mf/`); итоги переносятся в `docs/stand-review/`.

Для каждого набора из твоего списка (slug — имя с `_` вместо пробелов и `/`):

- `S/sheets/<slug>__NN.png` — листы стенда (все листы набора прочитай инструментом Read, каждый). На листе — ячейки с подписью сверху:
  - `Light|Dark · EMCD|Geometria|WL Default · Web|iOS|Android · L0` и для EMCD `Web · L1…L3` — в каждой ячейке экземпляры ВСЕХ вариантов набора в порядке набора;
  - `Текст · long|de|ar|hi|th|ja|kk` — вариант по умолчанию с длинным текстом и языками во всех текстовых свойствах (ширина ячейки 360);
  - `Текст 200 % · все варианты` — все варианты с удвоенным кеглем;
  - `Свойство · X = On|Off` — каждое булево свойство переключено из значения по умолчанию, все варианты.
  Пурпурный фон между ячейками — подложка листа, не дефект.
- `S/descs/<slug>.txt` — описание набора в Figma (правила, когда использовать, a11y, legacy).
- `S/mf/<slug>.json` — выжимка манифеста: оси (`axes`), варианты, свойства (`props`), вложенные (`nested`), min / max, служебные слои (`layers`), токены, борды.
- Образцы записей контракта: `/srv/emcd-design-tokens/scripts/contract-data.mjs` (прочитай шапку с константами и записи `Amount`, `Avatar`, `Badge`, ещё 1–2 похожие на твои наборы). Модель состояний и общие правила, если нужно: `/srv/emcd-design-tokens/docs/components.md`, `docs/service-layers.md`, `docs/sizing.md`.

## Что сделать

### 1. Просмотр (глазами, по каждому листу)

Ищи реальные дефекты отрисовки, а не вкусовые:
- цвет не меняется в Dark / бренде там, где должен; элемент не виден или почти не виден на L0–L3 (контраст с подложкой), в Dark, в Geometria или WL;
- вариант выглядит сломанным: обрезка, наложение слоёв, пустой вариант, неверный порядок, текст вылезает за границы, разная высота у вариантов одной оси без причины;
- состояния: Hover / Pressed / Focus / Disabled / Error / Skeleton неотличимы или противоречат описанию; Disabled у вложенных не погашен;
- длинный текст и языки: не усекается и не переносится по правилу описания, ломает раскладку; арабский / хинди / тайский обрезаны по высоте;
- 200 %: текст обрезан по высоте или налезает (усечение по ширине многоточием у элементов с max-width — не дефект, отметь как заметку);
- свойства: переключение ничего не меняет, ломает раскладку, служебные слои (Focus ring, Show hit area, Safe margin) не появляются или выглядят неверно;
- платформы: iOS / Android ничем не отличаются от Web — нормально, если по описанию размеры не зависят от платформы; отметь только явную поломку.

На каждое замечание укажи: лист, подпись ячейки, какой по счёту экземпляр (или какие), что видно и чего ждали. Не выдумывай: если не уверен, пометь `? ` в начале. Если всё чисто — так и напиши.

### 2. Запись контракта

Напиши запись для массива `DATA` в стиле образцов: объект JS (литерал), поля как у `Amount`:
`name, identity?, what, use, dont, rule[], never?, anatomy[], group, states[], defaults{}, propsNote?, content[], events[], behavior[], a11y[], platforms, accept, migration[], todo[]`.

- Опирайся на описание Figma и манифест; не придумывай фактов (чисел, токенов, имён свойств), которых там нет. Имена осей, значений и свойств — точно как в манифесте. `defaults` — значения осей первого варианта в манифесте (вариант по умолчанию).
- `rule` — жёсткое правило выбора на каждую ось и на значимые свойства (одна задача — один способ).
- `group`: одна из констант `PLASHKA`, `SELECT`, `TEXTUAL`, `NONE` (можно `NONE + '; Skeleton — загрузка'`) или строка. `states` — что означает каждое значение оси State и как выглядит.
- `content`: длинный текст (можно `LONG(n)` если есть max-width n), языки и RTL (`RTL` или своя строка), 200 % — по тому, что ты увидел на стенде («Проверено на стенде: de, ar, hi, th, ja, kk» — только если действительно чисто).
- `events`, `behavior` (движение, тайминги из описания; можно `MOTION`), `a11y` (роль, клавиатура, имя; `FOCUS`, `ZONES` где есть служебные слои).
- `platforms`: `PLATFORMS` (интерактивные) или `PLATFORMS.slice(0, 1)` (неинтерактивные); если компонент только для Web или только для App — своя строка массивом.
- `accept`: `{ audit: OK, vc: OK, ap: '0 (2026-11-13)', not: 'полный крест N ячеек — на стенде 2026-11-13 просмотрены 24 (Light / Dark × EMCD / Geometria / WL × Web / iOS / Android на L0 и L1–L3 для EMCD Web), длинный текст, 6 языков, 200 %, булевы свойства; кода нет — parity props пропущена' }`, где N = 72 (2 темы × 3 бренда × 3 платформы × 4 уровня). Если в описании `Code: HTML/CSS ✓` — вместо «кода нет — parity props пропущена» напиши «код — HTML/CSS».
- `migration`: строка(и) из Legacy в описании: «DS Web … → оси / свойства».
- `todo`: только реальные остатки (например, временные значения числом, ждущие токена); иначе `[]`.
- Язык — русский, коротко, без воды, в стиле образцов. В строках используй одинарные кавычки JS, внутри текста — «ёлочки» и обратные апострофы для имён токенов / слоёв.

## Куда писать

- `S/review/<slug>.md` — замечания:
  ```
  # <Имя набора>
  Листов просмотрено: N из N
  ## Дефекты (править в Figma)
  - [лист NN · «подпись ячейки» · экземпляр k] что видно → чего ждали
  ## Заметки (не дефект / на решение)
  - …
  ```
  Нет дефектов — «нет».
- `S/entries/<slug>.mjs` — ровно один объект-литерал, начинается с `{` и кончается `},` (как элемент массива), без `export`. Проверь синтаксис: `node -e "const PLASHKA='',SELECT='',TEXTUAL='',NONE='',ZONES='',FOCUS='',MOTION='',PLATFORMS=['',''],RTL='',OK='',LONG=()=>'',INPUT_ADDON={};const x=[$(cat файл)];console.log(x[0].name)"` должен напечатать имя.

В конце верни короткую сводку: по каждому набору — число дефектов и одна строка о главном.
